1. Inodes and Metadata:
In the `inode_inspector.py` script, we printed the "Inode Number". If you rename the file using the Linux `mv` command, will the Inode Number change? Why or why not? (Hint: Think about how the OS separates the file name from the actual data).
Ans: No, the Inode Number will not change. The OS stores the file name in the directory table, entirely separate from the actual file data 
and metadata (which the inode holds). Renaming a file only updates the directory entry, leaving the underlying inode untouched.

2. POSIX Permissions:
If you want to set a file's permission so that the Owner has Read/Write/Execute (7), the Group has Read/Execute (5), and Others have absolutely no access (0), what would be the 3-digit octal number you pass into `os.chmod()`? 
Ans: The 3-digit octal number you would pass is 0o750.

3. The AI Context:
Why is it safer to rely on Operating System file permissions (like `os.chmod(0o444)`) to protect production model weights rather than relying solely on application-level logic or Python try-except blocks?
Ans: OS-level permissions are strictly enforced by the OS Kernel itself, acting as an absolute barrier. As shown in the scenario, if someone accidentally runs a script that opens the multi-million dollar model in write mode, 
the kernel instantly denies access and averts disaster. Application-level logic is prone to bugs or human error, whereas OS-level protection is foolproof.
